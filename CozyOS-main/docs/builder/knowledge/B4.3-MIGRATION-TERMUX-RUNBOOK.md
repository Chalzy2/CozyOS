# B4.3 — Migration Blocker: Exact Termux Runbook

This is the exact sequence to close the final B4.3 blocker for real. It
cannot be executed from this Cloud sandbox — no network egress exists
here (confirmed again this round: `curl` to any external host returns
`403`, and `apt-get install postgresql` fails the same way). Everything
below has been syntax-checked and, where possible, dry-run tested in
this sandbox against a mock/SQLite substitute — never against real
PostgreSQL, which is the whole point of running it for real from Termux.

**Do not point `<neon-url>` below at any production database. Use a
disposable Neon branch/database created specifically for this test.**

---

## Step 0 — one-time setup

```
cd "CozyOS Merged 0003"     # the checkpoint root
npm ci
```

## Step 1 — build the two disposable SQLite fixtures

```
node scripts/b4.3/build-migration-test-fixtures.js
```

This prints two paths — copy them, you'll need both:
```
Clean (happy path):        /tmp/.../clean.sqlite
Broken FK (rollback test): /tmp/.../broken-fk.sqlite
```

The clean fixture has representative, relationally-consistent data
across all 10 application tables (2 users — one platform admin — a
credential, a challenge, a session, a password reset token, a recovery
code, a pending auth session, an organization, a membership, an audit
event). The broken one is identical, plus one extra credential row
pointing at a `user_id` that doesn't exist — a real, unmodified foreign
key violation that PostgreSQL's actual schema will reject.

## Step 2 — happy-path migration (real Neon target)

```
node server/webauthn-rp/migrate-sqlite-to-postgres.js \
  --sqlite /tmp/.../clean.sqlite \
  --database-url "<neon-url>"
```

**Expect:** the script prints `Source (SQLite): ...` and
`Target (PostgreSQL): postgres://<host>/<db>` — **check this line
yourself: it must never contain a username or password**, only the host
and database name. Then per-table counts, then
`Verification passed: source and target row counts match for every table.`

**Verify migration succeeded / IDs preserved / row counts match /
foreign keys valid** — connect with `psql "<neon-url>"` (or any client)
and run:

```sql
SELECT id, email FROM users ORDER BY id;
-- expect exactly: user-1 | admin@example.test
--                 user-2 | member@example.test

SELECT credential_id, user_id FROM credentials;
-- expect: cred-1 | user-1   (the FK is valid — user-1 exists)

SELECT organization_id, user_id FROM organization_memberships;
-- expect: org-1 | user-2   (both FKs valid)

SELECT count(*) FROM users;              -- expect 2
SELECT count(*) FROM credentials;        -- expect 1
SELECT count(*) FROM challenges;         -- expect 1
SELECT count(*) FROM sessions;           -- expect 1
SELECT count(*) FROM password_reset_tokens; -- expect 1
SELECT count(*) FROM mfa_recovery_codes; -- expect 1
SELECT count(*) FROM pending_auth_sessions; -- expect 1
SELECT count(*) FROM organizations;      -- expect 1
SELECT count(*) FROM organization_memberships; -- expect 1
SELECT count(*) FROM audit_events;       -- expect 1
```

If every count and every ID matches the above, the happy path is proven
for real.

## Step 3 — non-empty target protection

Immediately re-run the exact same command from Step 2 again, against the
same now-populated target:

```
node server/webauthn-rp/migrate-sqlite-to-postgres.js \
  --sqlite /tmp/.../clean.sqlite \
  --database-url "<neon-url>"
```

**Expect: it refuses**, printing something like `users already has 2
row(s). Refusing to import into a non-empty table without --force.` and
exits non-zero. **Then re-run the count queries from Step 2 — they must
be unchanged (still exactly 1 or 2 of everything, not doubled).** If
counts doubled, the refusal didn't actually prevent a second import —
that would be a real bug, not something currently expected.

## Step 4 — rollback-on-injected-failure (real Postgres constraint, not a mock)

Get a **second, separate, empty** disposable database/branch — do not
reuse the one from Steps 2–3, since it's intentionally non-empty now.
Then:

```
node server/webauthn-rp/migrate-sqlite-to-postgres.js \
  --sqlite /tmp/.../broken-fk.sqlite \
  --database-url "<second-empty-neon-url>"
```

**Expect: it fails**, with an error mentioning a foreign key violation on
the `credentials` table, and the script's own message
`Import failed and was rolled back (PostgreSQL left unchanged): ...`.

**Then check this second target is completely empty:**
```sql
SELECT count(*) FROM users;         -- expect 0
SELECT count(*) FROM credentials;   -- expect 0
SELECT count(*) FROM organizations; -- expect 0
-- (and so on for every table)
```

The critical check: **`users` must be 0, not 2.** The clean fixture's 2
users are inserted successfully (they're first in the FK-safe table
order) before the credentials-table failure happens later in the same
transaction. If `users` shows 2 rows here, the transaction did not
actually roll back completely — that would be a real, serious defect.
If it's 0, rollback is proven for real.
