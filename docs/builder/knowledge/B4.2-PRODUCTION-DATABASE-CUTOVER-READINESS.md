## 1. Database configuration

**PASS (adapter layer) / BLOCKED (production entrypoint) — mixed result, evidence below.**

- `server/webauthn-rp/database-adapter.js`'s `createDatabaseAdapter()` is
  the single explicit selection point: `databaseUrl` present → PostgreSQL
  (throws if `pg` can't load or connect — never falls back); `sqliteDb`
  present → SQLite; **neither present → throws** (`"neither databaseUrl
  nor sqliteDb was provided. Refusing to guess a database."`). Verified
  directly in source. This part is genuinely safe: no silent fallback,
  no default database.
- `server/webauthn-rp/server.js`'s `createServer()` correctly threads
  `databaseUrl` through to `createDatabaseAdapter()` when provided,
  `openDb()`/SQLite otherwise. Verified directly in source.
- **Concrete defect found:** `server/static-boundary-server.js` is the
  actual process entrypoint (`if (require.main === module)` block at the
  bottom of the file — this is what runs when the process is started,
  e.g. by a Render/render.yaml Start Command). This block builds its
  config from `process.env.COZY_WEBAUTHN_DB`, `COZY_RP_ID`,
  `COZY_RP_ORIGIN`, `COZY_FIREBASE_PROJECT_ID` — **it never reads
  `process.env.COZY_DATABASE_URL` and never passes a `databaseUrl` key
  into `createBoundaryServer({...})` at all.**
  - The `createBoundaryServer()` factory function itself *does* accept
    and correctly thread a `databaseUrl` parameter (confirmed in source,
    a few lines above), and its own comment states: *"Fixed: databaseUrl
    is now the single selector for BOTH this file's own `rp` instance...
    and the mounted WebAuthn RP API, so the whole process agrees on one
    backend."*
  - That comment describes a real fix to the **factory function's**
    parameter plumbing. It does **not** describe the actual boot code
    path at the bottom of the file, which was not updated to read the
    env var. I verified this by reading the literal `require.main`
    block: the object passed to `createBoundaryServer(...)` has no
    `databaseUrl` key.
  - **Practical consequence: setting `COZY_DATABASE_URL` in the real
    deployment environment today would have zero effect.** The process
    would still silently open its local SQLite file, contradicting both
    the comment's claim and this gate's requirement of "no silent SQLite
    fallback."
- **Missing-config failure behavior:** correctly verified safe at the
  adapter layer (throws, doesn't guess) — but this doesn't help if the
  entrypoint never forwards the value that would trigger PostgreSQL
  selection in the first place.

**This is a concrete, code-level blocker**, not a guess: `grep`-verified
absence of `databaseUrl`/`COZY_DATABASE_URL` anywhere in the
`require.main` block of `server/static-boundary-server.js`.

## 3. Database adapter

**PASS.**

- `PostgreSQLDatabaseAdapter.transaction()`: opens a dedicated client
  from the pool, runs `BEGIN`, invokes the callback with a
  transaction-scoped adapter instance, `COMMIT`s on success,
  `ROLLBACK`s on any thrown error (with a defensive try/catch around the
  rollback itself in case the connection is already broken), and always
  `release()`s the client in a `finally` block. Verified directly in
  source; confirmed behaviorally by the B3 evidence's passing
  "transaction commits all statements together" and "transaction rolls
  back ALL statements when an error is thrown partway through" tests.
- Nested transactions are explicitly rejected
  (`"PostgreSQLDatabaseAdapter.transaction(): nested transactions are
  not supported."`) rather than silently misbehaving.
- Connection/pool lifecycle: `close()` calls `pool.end()` when available;
  `run-migrations.js`'s standalone `Client` is `.end()`ed in a `finally`
  block regardless of success/failure.
- Placeholder conversion (`?` → `$1,$2,...`) is a pure, separately
  exported, separately unit-testable function
  (`toPositionalPlaceholders`), confirmed passing by name in the B3
  evidence's first test.
- Error propagation: no `catch` block anywhere in the adapter swallows an
  error without either re-throwing or explicitly returning a documented
  failure shape — verified by reading every `catch` in the file.

## 7. Security

**PASS, with one disclosed gap.**

- No database credentials or connection strings are committed anywhere
  in the checkpoint (re-confirmed this session — same secret scan as
  B4.1, no new findings).
- No secrets logged: `static-boundary-server.js`'s startup log prints
  `emailProvider.status()`, explicitly documented as never including

  `console.log`/`console.error` call in these three files — none
  interpolates `databaseUrl`).
- **TLS: not code-enforced, relies on connection-string convention.**
  `new Pool({ connectionString: databaseUrl })` in `database-adapter.js`
  passes no explicit `ssl` option — TLS is only in effect if the supplied
  connection string itself requests it (e.g. Neon's default URLs include
  `sslmode=require`, and the closed B3 evidence's own console warning
  confirms the test run's connection string did include an `sslmode`
  parameter). If an operator supplied a bare `postgres://user:pass@host/db`
  with no `sslmode`, the connection would not be encrypted and nothing in
  the application would object. **This is a disclosed gap, not a pass**
  — recommend the adapter itself require/default to
  `sslmode=require`/`verify-full` rather than depending on every operator
  to include it in the URL.
- Production admin bootstrap remains explicit and non-network-reachable:
  confirmed by direct reading of `bootstrap-admin.js`'s header and
  `rp.js`'s own comment that `setPlatformAdmin()` is "deliberately never
  wired to any HTTP route."
- No fail-open behavior found anywhere in the adapter, the migration
  runner, or the admin-gate path (`chalzydashboard.html`'s gate, audited
  under B4.1, fails closed on network/parse errors).

## 9. Recovery / rollback plan

- **How PostgreSQL would be selected:** set `COZY_DATABASE_URL` in the
  deployment environment. **Currently this has no effect** — see the §1
  blocker. Once fixed, setting/unsetting this one variable is the
  intended full selection mechanism; no code branch elsewhere needs to
  change.
- **How to detect failure:** `createDatabaseAdapter()` throws
  synchronously-in-effect (a rejected promise from the first query, or a
  connection error from `pool`) rather than degrading silently — an
  operator would see the process crash or fail health checks immediately,
  not experience a slow data-integrity problem. No automatic retry/fallback
  exists that could mask a failure.
- **How to stop rollout:** unset `COZY_DATABASE_URL` (once §1 is fixed to
  actually honor it) and restart the process — it falls back to the
  existing SQLite path with no other configuration change needed, per
  `createServer()`'s ternary.
- **How to restore the previous database configuration:** the SQLite
  file itself is untouched by any PostgreSQL work — `migrate-sqlite-to-postgres.js`
  is a one-way export tool; nothing in this codebase deletes or mutates
  the SQLite file when PostgreSQL is selected. Restoring is simply
  re-deploying without `COZY_DATABASE_URL` set.
- **Data migration concerns:** `migrate-sqlite-to-postgres.js` exists to
  move existing SQLite data into Postgres, but **this session performed
  no test of that specific script against real data** (it wasn't part of
  the closed B3 16-test suite, which builds its Postgres schema fresh via
  migrations rather than importing SQLite rows). **Marking the SQLite→Postgres
  data migration path UNTESTED** — schema readiness is proven; a real
  data-carrying cutover would additionally need this script verified
  against a realistic data snapshot first.
- **What must be backed up before an actual production cutover:** the
  full production SQLite database file, taken immediately before cutover;
  the pre-cutover `COZY_DATABASE_URL`-unset deployment configuration
  (so rollback is a one-variable change, not a redeploy from scratch);
  and a fresh export from `migrate-sqlite-to-postgres.js` should be
  taken and spot-checked against the live SQLite file's row counts
  before any real traffic is pointed at Postgres.

## Repair (this round)

### Original defect

`server/static-boundary-server.js`'s actual process entrypoint — the
`if (require.main === module)` block, which is what runs when the
process boots (e.g. a Render Start Command) — built its config from
`COZY_WEBAUTHN_DB`, `COZY_RP_ID`, `COZY_RP_ORIGIN`, and
`COZY_FIREBASE_PROJECT_ID`, but never read `process.env.COZY_DATABASE_URL`
and never passed a `databaseUrl` key into `createBoundaryServer({...})`.
The factory function itself already supported the parameter correctly —
only the boot script that calls it was missing the wiring.

### Exact repair

Two changes, both confined to `server/static-boundary-server.js`'s
`require.main` block (no other file's application logic was touched):

1. Added `const databaseUrl = process.env.COZY_DATABASE_URL;` and passed
   `databaseUrl` into the `createBoundaryServer({...})` call — the same
   pattern already used for every other env-driven option in that block.
2. Added one boot-log line reporting which backend was actually selected
   (`"Database backend: PostgreSQL (COZY_DATABASE_URL set)"` or
   `"...SQLite (COZY_DATABASE_URL not set)"`), so an operator watching
   the boot log has direct visibility into the decision — the operator-facing
   half of "no silent fallback." **The connection string itself is never
   logged** — only whether one was present (verified: `grep -n
   databaseUrl server/static-boundary-server.js` shows it used only in a
   boolean ternary inside this log line, never interpolated directly).

**No new fallback logic was introduced.** `createBoundaryServer()` →
`createDatabaseAdapter()`'s existing behavior is unchanged and was not
touched: `databaseUrl` present → PostgreSQL, throwing (not falling back)
if `pg` can't load or connect; `databaseUrl` absent → the existing SQLite
path via `openDb(dbPath)`. The fix only ensures the environment variable
that was always supposed to reach this decision point now actually does.

### New regression test

`server/test/static-boundary-entrypoint-database-selection.test.js` —
this is the first test in the checkpoint that actually spawns
`static-boundary-server.js` as its own process (via `child_process.spawn`),
which is necessary because `require.main !== module` when a file is
`require()`d by another test — every existing test exercises
`createBoundaryServer()` directly and therefore never ran the boot block
this defect lived in. Two tests:

1. **`COZY_DATABASE_URL` unset → boots normally, logs SQLite selection**
   (regression guard proving unchanged prior behavior for the common
   case).
2. **`COZY_DATABASE_URL` set (to a syntactically valid but unreachable
   target) → logs PostgreSQL selection, and the configured SQLite file
   is never created.** I initially assumed an unreachable PostgreSQL URL
   would cause the boot itself to fail fast; testing revealed
   `node-postgres`'s `Pool` connects **lazily** (no socket opens until
   the first query), so the HTTP server does start listening in this
   case — that's correct, existing `pg` behavior, not a new fallback.
   The test was corrected to assert the actually-deterministic signals:
   the boot log explicitly names the selected backend, and the SQLite
   file at the configured path is provably never opened.

Both tests: **2/2 PASS**, run this session.
