## Blocker 3 addendum — real Neon execution found and fixed a test bug

The operator ran `postgres-recovery-code-runtime.test.js` for real, from
Termux, against real Neon. Result: **4/5 pass**, one failure:

```
tests: 5, pass: 4, fail: 1, skipped: 0
Failed: recovery codes: transactional consistency — redemption failure
never leaves a code half-consumed
AssertionError: recovery code must be marked used
actual: null, expected: true
```

Raw evidence preserved unedited at
`docs/builder/knowledge/B4.3-RECOVERY-CODE-RUNTIME.txt`.

**Diagnosis: this is a defect in the test's own verification query, not
in the production recovery-code implementation.** The failing assertion
used:

```sql
SELECT used_at FROM mfa_recovery_codes
WHERE user_id = ? AND code_hash IS NOT NULL
ORDER BY used_at DESC LIMIT 1
```

`code_hash IS NOT NULL` is a no-op — `code_hash` is the table's primary
key and is never null — so this matched **all 10** of the user's
recovery codes (9 untouched, `used_at IS NULL`; 1 redeemed). It relied
entirely on `ORDER BY used_at DESC LIMIT 1` to surface the redeemed one.

PostgreSQL's documented default for a `DESC` sort is `NULLS FIRST`
(NULL treated as greater than any value). SQLite's default is the
opposite, `NULLS LAST`. I confirmed this empirically in this sandbox
rather than relying on memory of the docs:

```
SQLite ORDER BY v DESC on rows (NULL, 100, NULL)
→ [{v:100}, {v:null}, {v:null}]   — non-null value sorts FIRST
```

So on SQLite the flawed query happened to return the redeemed row every
time, masking the bug. Against real PostgreSQL, the same query
correctly-per-spec returned one of the 9 untouched `NULL` rows first —
exactly the observed `actual: null`.

**Confirmed NOT a production bug, two independent ways:**
1. `RelyingParty.completePendingAuthWithRecoveryCode()` in `rp.js` never
   uses `ORDER BY`/`LIMIT` to find the row it updates — it targets the
   exact `code_hash` (primary key) directly, for both the lookup and the
   `UPDATE`. No ambiguity on any database.
2. Test 2 in the same file, using the *correct* pattern
   (`WHERE user_id = ? AND used_at IS NOT NULL`, no `ORDER BY`), **passed**
   against this same real Neon run — independently confirming the actual
   redemption/consumption behavior is correct in production.

**Fix applied** (test file only, no production code touched): corrected
the query to the same proven-correct pattern test 2 already uses, and
removed the now-unnecessary `ORDER BY`/`LIMIT` — exactly one row is
expected to match, so the filter alone is sufficient and is unambiguous
regardless of any database's NULL-ordering default.

**Re-verified via the same discipline as before**: a temporary scratch
copy run against SQLite (not Postgres, not the checkpoint — deleted
immediately after) confirmed **5/5 PASS** with the fix applied.

### `B4_3-MIGRATION-REAL-NEON-RUNTIME.txt` (233 bytes, SHA-256 `b8fab57e...`)

Complete content:
```
Source (SQLite): /data/data/com.termux/files/usr/tmp/cozyos-b4.3-migration-fixtures-E5CbhG/clean.sqlite
Target (PostgreSQL): (unparseable connection string — not logging it)
migrate-sqlite-to-postgres: str.charAt is not a function
```

This is real: the source path matches exactly what
`build-migration-test-fixtures.js` produces on a real Termux filesystem.
But **the migration never attempted a PostgreSQL connection — it
crashed before that point**, and none of the six requested checks
(clean migration, counts, refusal, rollback, etc.) were exercised at
all.

**Root cause, traced to source:**

1. `redactConnectionString()` (the function that logged
   `Target (PostgreSQL): ...`) has its own `try { new URL(databaseUrl) }
   catch { return '(unparseable...)' }` — it caught a parse failure and
   printed the safe fallback. This means `databaseUrl` was already not a
   valid URL string at this point.
2. The actual crash, `str.charAt is not a function`, comes from
   `node_modules/pg-connection-string/index.js:10` —
   `if (str.charAt(0) === '/') {` — inside `pg`'s own connection-string
   parser, which assumes `str` is a String.
3. Tracing backward: `parseArgs()` in the migration script has this
   logic for every CLI flag: `const value = argv[i + 1] &&
   !argv[i + 1].startsWith('--') ? argv[i + 1] : true;` — **if the next
   argv token is missing or looks like another flag, the value becomes
   the boolean `true`, not a string.**
4. This happens whenever a connection string isn't quoted safely in the
   shell. Neon connection strings routinely include
   `&channel_binding=require` and `&sslmode=require` in their query
   string — an **unquoted `&` is bash's background-job operator**,
   which silently truncates the argument right there. This is an easy,
   common mistake, not an exotic one.
5. `databaseUrl === true` (a boolean) is truthy, so it passed every
   `if (!databaseUrl)` check in the script, reached
   `new (require('pg').Client)({ connectionString: true })`, and crashed
   three dependency layers down with a message that gives no hint about
   the real cause.

**This is a genuine defect in the migration script's error handling** —
not a production security bug, not data corruption, but a real
usability/robustness gap that this exact real-world run surfaced. Per
this gate's standing instruction ("If the migration script itself has a
defect, repair it minimally and add regression coverage"), it was fixed:

**Fix applied** (`server/webauthn-rp/migrate-sqlite-to-postgres.js`):
1. `migrate()` now validates `typeof databaseUrl === 'string'` before
   doing anything else, throwing a clear, actionable error naming the
   likely cause (unquoted `&`) and two concrete fixes (quote the value,
   or use the `COZY_DATABASE_URL` environment variable instead).
2. `main()`'s fallback chain (`flags['database-url'] ||
   process.env.COZY_DATABASE_URL`) had a compounding bug: if the CLI
   flag resolved to the truthy boolean `true`, it would never fall
   through to check the environment variable either — even if
   `COZY_DATABASE_URL` was correctly set as a safety net. Fixed to only
   use the CLI flag when it's actually a string.

**Reproduced the exact real-world crash directly** to confirm the fix:
calling `migrate({ databaseUrl: true, ... })` now throws the new clear
message instead of the old dependency stack trace — verified in this
session, not assumed.

**Regression coverage added** — two new tests in
`migrate-sqlite-to-postgres.test.js`:
- Confirms `databaseUrl: true` fails with the new clear error message,
  caught before ever reaching a Postgres client construction.
- Confirms the `main()` fallback logic no longer shadows a valid
  `COZY_DATABASE_URL` environment variable when the CLI flag is
  malformed.
