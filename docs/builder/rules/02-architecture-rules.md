| 52 | Architecture Ambiguity Classification — When two or more sources already in the verified workspace describe a module's responsibility in ways that don't obviously reconcile, Builder shall not assume they describe the same engine, and shall not assume they describe different engines. | 53 | ZIP Classification Protocol — Before doing any work on an uploaded ZIP, Builder shall classify it as exactly one of four types, and only a **Main Production ZIP** may ever receive a new production version number or a production-milestone certification: (1) **Main Production ZIP (Authoritative)** — the complete CozyOS repository; the only ZIP eligible to become a new numbered production milestone (e.g. M373); all Builder work is eventually merged here. (2) **Builder Patch ZIP** — contains only files Builder created or modified, used to transfer Builder's own work; cannot become a production release by itself. (3) **Builder Documentation ZIP** — rules, reports, registries, certifications, knowledge; supports Builder's learning and continuity; never replaces the production repository. (4) **Feature / Module ZIP** — a partial repository for one feature or subsystem, used for development and review; must eventually be merged into the Main Production ZIP. Classification test: does this ZIP contain the complete CozyOS repository? If yes, work directly on it and produce a new Production ZIP under Rule 1/Rule 13. If no, treat it as a patch, documentation package, or feature workspace: learn from it, analyze it, generate reports and suggestions, create patch files if needed — but do not increment the production version, and do not certify it as a production release. Hold that work until a real Main Production ZIP is available, then merge into it (per Rule 6/Rule 24 — compose into the existing authoritative repository, never fork a parallel one). This keeps one authoritative CozyOS version history while still letting Builder work productively on smaller ZIPs. **Registry gate (added — the workspace-classification corollary):** a Missing Dependency (`MD-NNN`) registry entry may only be opened after Builder has confirmed which of the four workspace types it is currently working from. A Builder Patch ZIP, Builder Documentation ZIP, or Feature/Module ZIP not containing a file is never, by itself, evidence that file is missing from CozyOS — it only proves the file isn't in *that* smaller workspace. Before logging `MD-NNN`, Builder must confirm the file's absence against the actual Main Production ZIP if one has been supplied in this session or is otherwise available; if no Main Production ZIP is available yet, the record must say so explicitly ("workspace type: Builder Patch ZIP — production-wide absence not yet confirmed") rather than implying the file is missing from CozyOS itself. | Adopted this pass, in direct response to how the two M372 ZIPs were actually used: `CozyOS-M372-BuilderObservation-Complete.zip` was correctly treated as the Main Production ZIP (worked on directly, produced `CozyOS-main-M372-BuilderIntegration.zip`); `CozyOS-Builder-SessionHandoff-M372.zip` was correctly treated as a Builder Patch ZIP (files Builder created/modified, merged into the authoritative repo, never itself certified as a production release) — this rule formalizes that distinction going forward rather than leaving it implicit. **Registry-gate clause added retroactively in direct response to MD-001/AA-001**: both were opened against a Builder-only package that never contained `understanding-engine.js`, which was silently read as "missing from CozyOS" rather than "missing from this smaller workspace" — the file was present in the Main Production ZIP the entire time (see `reports/layer2-compose-analysis-AA-001.md`). This clause exists specifically so that mistake cannot recur. |

## Auto-discovered structural conventions (not written down anywhere as a numbered rule, but consistent across every file read)
- IIFE modules register onto a single `window.CozyOS` global namespace.
- Coordinators declare, in a header comment, exactly what they own vs. what they merely compose ("Canonical Ownership Declaration" pattern).
- Version guards: re-executing a script with a version mismatch throws `VERSION_CONFLICT` rather than silently overwriting (seen in `AuthCoordinator`, `module-registry.js`, others).
- `getDiagnosticsReport()` / `getAuditLog()` / `getVersion()` are near-universal public methods across coordinators — an implicit interface contract worth formalizing.
