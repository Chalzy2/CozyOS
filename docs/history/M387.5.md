# M387.5 — Browser Verification & Integration

**Baseline:** M387 | **Mode:** Verification + proven-issue fixes only (no new features, no architecture changes) | **Date:** 2026-08-06

## Objective

Verify Living Engine integration (M372–M387) in a real browser (real Chromium via
Playwright, not Node/vm simulation) before any further engine work. Fix only what
browser verification actually proved broken.

## Environment

- Real Chromium 141 (`chromium-1194`, Playwright 1.56.0), launched headless with
  `--no-sandbox`, driving the actual repository served over a local static HTTP
  server (`python3 -m http.server`, `127.0.0.1:8842`) — not a simulation, not a
  Node `vm` harness.
- This sandbox has no outbound internet access. Anything requiring an external
  network call (the Firebase CDN) could not be verified end-to-end here — see

  verification remain open for a follow-up pass — see "Remaining Scope" below.

## Round 1 — Initial Verification (pre-fix)

Five real, reproducible defects were found and confirmed by direct source
inspection (not guessed from the console message alone):

### Finding 1 — `core/modules/developer/developer-hub.css`: doubled `core/` path
- **Cause:** its 5 `@import url("../../core/ui/...")` lines were written as if
  the file lived one directory shallower than it does. From
  `core/modules/developer/`, two `../` reaches `core/`, so `../../core/ui/...`
  resolved to `core/core/ui/...` — a 404.
- **Evidence:** CDP `Network.requestWillBeSent` initiator trace showed all 5
  broken requests (`core/core/ui/cozy-tokens.css`, `core/core/shell/cozy-theme.css`,
  `core/core/shell/cozy-layout.css`, `core/core/ui/cozy-components.css`,
  `core/core/shell/cozy-animations.css`) originating from
  `core/modules/developer/developer-hub.css`, confirmed by reading its `@import`
  lines directly.
- **Consequence:** every theme profile failed `CozyTheme`'s token validation on
  `dashboard.html` (`"Theme ... rejected — missing required tokens"`), because
  the real token file never loaded.
- **Fix:** corrected the 5 `@import` paths to `../../ui/...` / `../../shell/...`.
- **Regression verification:** Round 2/3 — 0 `core/core/` requests, 0
  theme-rejection warnings on `dashboard.html`.

### Finding 2 — Global `SESSION_STATE` collision
- **Cause:** `core/modules/speech/cozy-speech.js` and
  `core/modules/vision/cozy-vision.js` both declare a bare top-level
  `const SESSION_STATE = Object.freeze({...})`, and neither file wraps its body
  in an IIFE (unlike the near-universal convention documented in
  `docs/builder/rules/02-architecture-rules.md`: "IIFE modules register onto a
  single `window.CozyOS` global namespace"). Loaded as two classic `<script>`
  tags on the same page, both `const`s land in the same script-level global
  scope, and the second `const SESSION_STATE` throws
  `SyntaxError: Identifier 'SESSION_STATE' has already been declared`.
- **Evidence:** reproduced directly in Chromium's console on `dashboard.html`;
  confirmed both files declare the identical identifier at top level, unwrapped,
  by direct source inspection.
- **Fix:** wrapped each file's entire body in `(function () { ... })();`,
  matching the codebase's own stated convention. No public API changed —
  `window.CozyOS.CozySpeech` / `window.CozyOS.Vision`-equivalent registrations
  at the bottom of each file still execute and still attach to `window`.
- **Regression verification:** Round 2/3 — the "already been declared" error no
  longer appears; both engines still register their globals (confirmed present
  in `window.CozyOS` enumeration).

### Finding 3 — `PluginManager` strict semver vs. real plugin manifests
- **Cause:** `core/pluginManager.js`'s `SEMVER_RE` was `/^\d+\.\d+\.\d+$/`
  (bare `major.minor.patch`, no pre-release suffix allowed), but 17 plugin
  files across ShopOS/MpesaOS/WholesaleOS/ChurchOS declare versions like
  `"1.0.0-ENTERPRISE"` — a real, standard semver pre-release label, just not
  one the regex accepted.
- **Evidence:** 17 repeated `[PluginManager] Invalid manifest.version '...'`
  console errors on `dashboard.html`; confirmed by grepping every
  `core/plugins/*.js` file's version constant.
- **Fix:** widened `SEMVER_RE` to
  `/^\d+\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?$/` (real semver, pre-release optional).
  Also updated `_compareVersions()` to strip everything from `-` onward before
  splitting/comparing numeric parts — this was necessary because the original
  strict regex existed specifically to prevent a `NaN` bypass in that same
  comparison function (see its own `[R-2]` comment); widening the regex
  without this second change would have silently reintroduced that bug.
- **Regression verification:** Round 2/3 — 0 "Invalid manifest.version" errors.
  (This fix did surface a *different*, previously-masked defect one step
  further into the registration pipeline — see Finding 6 below.)

### Finding 4 — `CozyPaymentProviderEngine` dependency/script-order break
- **Cause:** `core/modules/payment-provider/cozy-payment-provider-engine.js`
  requires 6 real internal modules to already be registered on
  `window.CozyOS.__PaymentProviderInternals` before it runs:
  `provider-registry.js`, `provider-manager.js`, `health-monitor.js`,
  `routing-engine.js`, `failover-engine.js`, `capability-engine.js`.
  `dashboard.html` never loaded 5 of the 6 — and the one `provider-manager.js`
  tag present pointed at an unrelated file (`core/shell/provider-manager.js`),
  not the payment-provider one.
- **Evidence:** the engine's own guard clause threw
  `"Required internal modules are not loaded. Load provider-registry.js, ..."`;
  confirmed by grepping `dashboard.html` for all 6 filenames and finding only
  the wrong file present.
- **Fix:** added the correct 6 `<script>` tags
  (`core/modules/payment-provider/provider-registry.js`,
  `.../provider-manager.js`, `.../health-monitor.js`, `.../routing-engine.js`,
  `.../failover-engine.js`, `.../capability-engine.js`) immediately before the
  engine's own script tag. Confirmed (by reading all 6 files) that none of
  them depend on each other, so any load order among the 6 is safe.
- **Regression verification:** Round 2/3 — 0 "Required internal modules are not
  loaded" errors; `window.CozyOS.LivingDecisionEngine` and siblings still
  present and in the same order.

### Finding 5 — `core/dashboard.js` uses ES `import` in a classic script
- **Cause:** the file opens with `import Permissions from './permissions.js';`
  and has a real `export default {...}` — genuine ES module syntax — but its
  `<script src="core/dashboard.js">` tag in `dashboard.html` had no
  `type="module"`.
- **Evidence:** `Uncaught SyntaxError: Cannot use import statement outside a
  module`, which aborted the entire file (and everything that depended on it
  loading).
- **Fix:** added `type="module"` to that one script tag. `type="module"` is
  already an established, working pattern elsewhere on the same page
  (`core/bridge/engine-bridge-bootstrap.js`), so this isn't a new pattern for
  the page to support.
- **Cascading discovery:** making `dashboard.js` a real module meant the
  browser now actually parsed its import, `core/permissions.js`, as a module
  too. That file turned out to end with a dead
  `window.CozyOS.Permissions = module.exports.default;` line — a leftover
  CommonJS-style bridge referencing the Node-only `module` global, which
  doesn't exist in a browser ES module and throws `ReferenceError: module is
  not defined`. Grepped the whole repo: nothing else reads
  `window.CozyOS.Permissions`, so this bridge line had zero real consumers.
  Removed it (2 lines) as the smallest fix that lets Finding 5's real fix stand
  without introducing a new error.
- **Regression verification:** Round 3 — 0 "Cannot use import statement" and 0
  "module is not defined" errors.

### Finding 6 — `PluginManager.register()` handler-type mismatch (16×)
**State at Round 1–3:** 🟡 Composed. **Current state (see Round 4/5 below): 🟢 Fixed.**
- **Cause:** `register(manifest, executionHandler)` requires
  `typeof executionHandler === "function"` (`[R-4]`, deliberate — "validate
  handler type at registration, not call time"). At least 16 plugin files
  (ShopOS/MpesaOS/WholesaleOS/ChurchOS) call
  `window.CozyOS.PluginManager.register(manifest, engineInstance)`, passing an
  **object** (the already-constructed engine instance), not a function.
- **Why it wasn't seen before:** Finding 3 (bad semver) threw first, on every
  one of these same plugins, before this line was ever reached. Fixing Finding
  3 let execution reach this second, independent validation, which then failed
  for the same 16 plugins for a different reason.
- **Evidence:** 16× `[PluginManager] executionHandler must be a function, got
  'object'.` in Round 2/3, confirmed against `register()`'s own source and one
  concrete call site (`core/plugins/shopOS-core.js:216`).
- **Status:** genuinely out of scope for "smallest possible fix" — fixing it
  means changing the call site in ~16 separate plugin files (wrap each
  `engineInstance` in a handler function, or relax/adapt the contract), which
  is a real, separate implementation decision, not a one-line correction.
  **Not fixed this round.** Recommended as the top item for the next pass.

### Finding 7 — `index.html` never links the theme token stylesheets
**State at Round 1–3:** 🟡 Composed. **Current state (see Round 4/5 below): 🟢 Fixed.**
- **Cause:** distinct from Finding 1. `index.html` only links
  `core/shell/cozy-animations.css`, `core/shell/launch-sequence.css`, and
  `core/living/cozy-living.css` — it never links `core/ui/cozy-tokens.css`,
  `core/shell/cozy-theme.css`, or `core/ui/cozy-components.css` at all (by
  any path, correct or not). `dashboard.html` gets tokens indirectly through
  `developer-hub.css`'s `@import` chain (which Finding 1 fixed); `index.html`
  has no such chain.
- **Evidence:** `CozyTheme` "rejected — missing required tokens" warnings for
  every theme profile persisted on `index.html` in Round 2/3, unchanged from
  Round 1, confirmed by grepping `index.html`'s own `<link>` tags.
- **Status:** not fixed this round — real fix requires deciding the correct
  file(s) to link (`core/ui/cozy-tokens.css` vs. `core/shell/cozy-tokens.css`
  vs. `core/shell/cozy-theme.css` all define overlapping-looking tokens; this
  needs the same kind of ownership check Rule 51 requires before touching it,
  not a guess). Flagged for next pass.

### Finding 9 — `EngineBridge` "playback" adapter uses a Node built-in
