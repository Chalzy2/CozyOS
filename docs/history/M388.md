# M388 — Living Media Interpreter (Compose Report)

**Phase:** Compose only. **Implementation: NO. Verification: NO. Repository
changes: none.** Per Rule 50 (Compose Before Implementation) and Rule 64
(No Milestone Jumping — M387.5 Completed, M388 unblocked to begin Compose).

## Objective

Interpret spoken language in media (downloaded video/audio, live streams,
movies, TV, meetings, voice calls) into any language CozyOS has learned,
while preserving original actors, video, lip movement as much as possible,
and background sounds/music. Target latency ~0.5s. This report identifies
what already exists in the repository versus what genuinely needs to be
built, before any engine is designed or written.

## Method

Direct source inspection only — every claim below is grounded in a real
file read, not assumed from a filename or a comment's aspiration. Where a
file's own header already discloses a boundary or a gap, that disclosure is
quoted/cited rather than re-derived, since these files were themselves
composed under the same Rule 50/51 discipline this report follows.

## 1. Existing Repository Capabilities

### Speech-to-Text (real, working)
- `core/modules/speech/adapters/speech-recognition-adapter.js` — real
  browser `SpeechRecognition`/`webkitSpeechRecognition` wrapper. Confirmed
  real (not simulated): searched for `webkitSpeechRecognition` /
  `SpeechRecognition(` construction, found in this file plus 4 others that
  each independently wrap it for their own narrow purpose (caption engine,
  cognitive coordinator, wake-word engine, hearing capability adapter) —
  none duplicate the recognition session itself; each composes the one
  real adapter.
- `core/modules/speech/cozy-speech.js` — the real Speech/Session/Language/
  Adapter Coordinator (confirmed earlier, M387.5 Finding 2 fix touched this
  file for an unrelated `SESSION_STATE` collision, so its shape is already
  well understood this milestone).

### Machine Translation (real orchestration; real MT itself is optional/browser-only)
- `core/modules/translate/cozy-translate.js` (1054 lines) — the real
  Translation Coordinator: sessions, streams, segments, translator
  directory, source/target `LanguageRegistry`. Its own header states, as a
  strict boundary: **"0% Text manipulation or string translation, 0%
  Language detection or linguistic modeling, 0% Audio/Speech generation or
  AI text processing."** It is orchestration only, by explicit design —
  never a translator itself.
- `core/modules/speech/adapters/speech-translation-adapter.js` — registers
  exactly one real translator record with `CozyTranslate`, seeds 15
  African + regional language codes (`sw, luo, ki, kam, kln, luy, mas, so,
  lg, am, yo, ha, zu, en, fr`) into its registry, and delegates the actual
  `translate(text) -> text` call to `window.CozyOS.SpeechTranslationProviders`.
  Its own header explicitly lists **NOT BUILT: "AI chat/assistant, voice
  authentication/verification, speaker recognition, translation AI models,
  cloud translation engine, offline translation models beyond a
  genuinely-detected browser API, voice cloning, auto language detection,
  streaming translation, speak-translation/TTS (future), a new Engine
  Bridge."**
- `core/modules/speech/adapters/speech-translation-provider.js` — the real
  provider registry behind the above. Its header: **"NEVER FABRICATE — No
  provider is invented here. If no provider is registered, every
  capability is honestly `false`."** Real detection: Chrome's experimental
  on-device `self.Translator` API, if present, is wrapped as a genuine
  offline-capable "browser-native" provider. **Cloud providers are an
  extension point only — none is implemented or bundled.**
- **Conclusion: real machine translation capability today is limited to
  whatever the end user's own Chrome build exposes via the experimental
  Translator API. There is no bundled, always-available MT engine for any
  of the 15 seeded languages.**

### Text-to-Speech / Voice (real, but narrow)
- `core/modules/speech/adapters/cozy-tts-browser-adapter.js` — generic Web
  Speech API TTS fallback (whatever voices the OS/browser exposes).
- `core/modules/speech/providers/charles-voice-provider.js` — plays back 2
  fixed, ~16s pre-recorded audio samples for known phrase keys. Its own
  header is explicit and load-bearing: **"This environment has no real,
  offline neural TTS / voice-cloning model capable of taking arbitrary
  CozyOS text ... and synthesizing it in Charles's actual voice. Building
  that is a real, separate, large piece of infrastructure (a
  trained/hosted voice model this platform does not have)."**
- `core/living-voice-style-engine.js`, `core/engines/voice/voice-engine.js`
  — real, but scoped narrowly (voice *style*/routing and a
  developer-identity Q&A voice responder respectively), not general
  arbitrary-text-to-preserved-speaker-voice synthesis.
- **Conclusion: no voice-cloning or neural TTS capability exists anywhere
  in this repository. This is the single largest, most explicitly disclosed
  gap for this milestone's "preserve original actors' voices" requirement.**

### Live Captions & Text Translation for real-time conversation (real, closest existing analog to "Meeting interpretation")
- `core/modules/communication/ldce-caption-engine.js` (Living Direct
  Communication Engine, Stage 3) — **real, TEXT-ONLY, working today**:
  composes `SpeechRecognitionAdapter` (real ASR) + `SpeechTranslationAdapter`
  (real MT orchestration, per above) + `LDCESessionEngine` (participant
  roster with real per-participant language preference) + `CozyConversation`
  (`addTranscriptSegment()` — captions ARE the transcript, no second
  store). Its own header explicitly states out-of-scope: **"speech-to-speech
  synthesis, emotion preservation, voice cloning."**
- **Conclusion: the text pipeline for live meeting captioning/translation
  (STT → MT → transcript) substantially already exists and works. The
  audio/video output pipeline (synthesized speech, dubbed audio, preserved
  video) does not.**

### Video/Media Coordination and Capture (real, partial)
- `core/modules/media/cozy-media.js` — the Enterprise Media Coordination
  Kernel: registry/metadata/lifecycle only, never transforms media itself,
  stores only adapter descriptors (confirmed by its own header, cited by
  `media-pipeline-manager.js` below).
- `core/engines/media/media-pipeline-manager.js` — the real Media Engine
  facade, owns pipeline sequencing only. Its own header states **LOCKED
  OWNERSHIP** (accepted, permanent): `Camera → camera-manager.js`,
  `Vision → cozy-vision.js`, `Audio → audio-manager.js`,
  `Playback → playback-engine.js`, `Scene → scene-manager.js` — **"Media
  Engine must never duplicate any of the above."** This is a real, existing
  ownership map any new engine in this milestone must respect.
- Of its 6 imported sub-engines: `image-engine.js`, `filter-engine.js`,
  `enhancement-engine.js` **exist**. `background-engine.js`,
  `codec-encoding-engine.js`, `codec-decoding-engine.js` **do not exist**
  anywhere in the repository (confirmed by `find`; this is exactly
  `MD-004`, already logged during M387.5, still open/deferred).
- `core/engines/camera/camera-manager.js`, `core/engines/audio/audio-manager.js`
  — real, working live capture/device-management engines (audio-manager.js
  was directly touched this milestone's predecessor, M387.5b/`AA-004`, so
  its real API — `registerProvider()`, device/mixer lifecycle — is already
  confirmed, not assumed).
- `core/engines/media/live-capture-engine.js`,
  `core/engines/video/live-video-capture-engine.js` — real webcam/live
  capture integration, confirmed touched during M387.5 (Finding 6, Finding
  9) so their real shape is already known.
- `core/engines/playback/playback-engine.js` — **confirmed Node.js-only**
  (imports `fs`, reads recorded session frames off real disk) during
  M387.5 Finding 9 — cannot run in a browser at all without a real,
  separate browser-storage-backed rewrite. Not reachable from any browser
  page today (its registration was removed from `engine-bridge-bootstrap.js`
  this same milestone chain, per `RP-012`).
- **Conclusion: no real video/audio codec (decode incoming file/stream,
  re-encode with new audio track) exists anywhere in this repository. This
  is the second-largest gap: without it, there is no way to take a
  downloaded video file, extract its audio, and produce an output video
  with dubbed audio and preserved video, regardless of what translation/TTS
  capability exists.**

### Room/Channel/Stream Coordination for multi-language live scenarios (real, structural only)
- `modules/live/cozy-live.js` (4341 lines) — a real, substantial
  coordination/graph layer: rooms, participants, speakers, language
  channels, subtitle channels, translation streams. Its own header states
  it **integrates with CozySpeech, CozyTranslate, CozyLanguage** and that
  **"actual translated content is produced by CozyTranslate/CozySpeech
  adapters and relayed"** — i.e. this file tracks structure and metadata
  only; it does not itself recognize, translate, or synthesize anything.
- **Conclusion: real, reusable scaffolding exists for "many participants,
  many language channels, many subtitle channels" — exactly the shape
  "Meeting interpretation" and "Live stream interpretation" need — but it
  is a directory, not a processing pipeline.**

### Lip Sync / Viseme / Face Landmark (does not exist)
- Searched for `lip.sync`, `lipsync`, `viseme`, `face.*landmark`,
  `MediaPipe` across the entire repository. No real hits — the only
  matches were unrelated files whose names loosely matched the regex
  (`provider-adapter-base.js`, `media-pipeline-manager.js`,
  `live-video-capture-engine.js` — none contain real lip-sync logic).
- **Conclusion: confirmed absent. Matches the task's own "Out of Scope
  (Current Compose): Lip-sync implementation" — no repository investigation
  contradicts deferring this.**

### "Learning model" / per-user learned languages (partial)
- `CozyTranslate`'s `LanguageRegistry` tracks which language *codes* are
  registered as valid source/target — a static seed list (15 codes today),
  not a per-user "languages this user has actually used/learned" model.
- `LDCESessionEngine`'s participant roster carries a real per-participant
  *language preference* (confirmed by `ldce-caption-engine.js`'s header),
  which is a genuine, existing building block for personalization — but it
  is a single current preference, not a learned history.
- `LivingAIContextEngine`, `LivingBehaviorEngine`, `LivingDecisionEngine`
  (M381–M387, all real-browser verified as of M387.5) are the closest
  existing "learns from real usage over time" infrastructure in the
  repository, but none of them currently ingest or reason about language
  usage at all — confirmed by re-reading their real, already-verified
  public APIs from M387.5's own investigation; none mention language,
  translation, or media.
- **Conclusion: no existing "learned languages" model. The closest
  reusable substrate is the Living Behavior/AI-Context/Decision chain's
  general pattern (real engines that learn from real signals), not any
  ready-made language-learning logic.**

### Plugin System (real; relevant only as a distribution mechanism)
- `core/pluginManager.js` (directly modified twice this milestone chain,
  `RP-009`/`RP-010`) — real plugin registration/execution kernel. No
  existing plugin performs language interpretation (confirmed: none of the
  19 real plugin manifests inspected during M387.5 — ShopOS, MpesaOS,
  WholesaleOS, ChurchOS, PharmacyOS, HospitalOS families — mention speech,
  translation, or media interpretation in their capabilities).
- **Conclusion: the plugin system is a real, available distribution
  mechanism for a future Living Media Interpreter, but contributes no
  existing interpretation logic itself.**

## 3. Proposed Living Engine Architecture — Reconciled Against What Exists

The task's proposed pipeline (`Media Input → Living Speech Engine → Living
Speaker Engine → Living Language Detector → Living Meaning Engine → Living
Translation Engine → Living Voice Engine → Living Media Mixer → Output`) is
evaluated stage-by-stage against Section 1/2's findings:

| Proposed stage | Reuse existing, or new build? |
|---|---|
| Living Speech Engine | **Reuse**: `speech-recognition-adapter.js` + `cozy-speech.js` already do this. A "Living" wrapper (if the Living-engine startup/registration convention — M381–M387's pattern — is required for consistency) would compose these, not replace them. |
| Living Speaker Engine (diarization) | **New build required.** No existing diarization capability (Section 2). |
| Living Language Detector | **New build required** for automatic detection. `speech-translation-adapter.js` explicitly disclosed this as NOT BUILT. |
| Living Meaning Engine | **Needs definition.** Not represented by any existing file or the task's own "Repository Composition Check" list — its intended responsibility (semantic understanding vs. literal MT?) is not yet composed. Flagged as an open question for Plan stage, not assumed here. |
| Living Translation Engine | **Mostly reuse.** `cozy-translate.js` (orchestration) + `speech-translation-adapter.js`/`-provider.js` (real delegation chain) already exist. The *actual* translation capability behind them (Section 2 — bundled MT) is the real gap, not the orchestration layer. |
| Living Voice Engine | **Reuse orchestration, new build for synthesis.** `voice-manager.js`/`cozy-tts-browser-adapter.js` exist for generic TTS; preserving the *original speaker's* voice (per this milestone's stated goal) requires the voice-cloning capability Section 2 confirms is entirely absent. |
| Living Lip Sync Engine | **New build required**, explicitly Out of Scope this Compose (per the task's own framing) — confirmed absent, not deferred by omission. |
| Living Media Mixer | **New build required.** `media-pipeline-manager.js` exists as a *pipeline sequencer* for image/filter/enhancement, but has no encode/decode/mux capability today (`MD-004`) — the mixer this milestone needs is a different, audio+video-aware capability than what exists. |
| Living Streaming Engine | **New build required**, explicitly disclosed as NOT BUILT anywhere. |
| Living Subtitle Engine | **Partial reuse.** `cozy-live.js`'s subtitle-channel structure + `ldce-caption-engine.js`'s real live-caption text pipeline are genuine building blocks; export/rendering (`.srt`, burn-in) does not exist. |

**This reconciliation is the primary deliverable of this Compose report** —
it directly answers the task's own "Repository Composition Check" and

## 4. Data Flow (Composed, Not Yet Designed in Detail)

At Compose stage, only the real, already-existing data-flow segments can
be described with confidence; the rest requires Plan-stage design once
new-engine ownership is settled (Section 6):

**Already-real segment (text-only, live-conversation case):**
`SpeechRecognitionAdapter` (real audio→text) → `CozyConversation.addTranscriptSegment()`
(real transcript store) → `SpeechTranslationAdapter.translateText()` (real
delegation to whatever MT provider is actually registered, honestly
`isReal:false` if none is) → `CozyTranslate.routeSegment()` (real
bookkeeping) → live caption display.

**Not yet real (media-file case, the milestone's primary "downloaded
video/audio" scope item):** no existing segment covers file input →
decode → speech extraction → (the above text pipeline) → TTS → re-encode →
output. Every arrow in that chain after "decode" either doesn't exist
(decode/encode/mixer) or is only partially real (TTS without voice
preservation). A full data-flow diagram for this case cannot be honestly
drawn yet — Section 2's gaps are load-bearing blockers for it, not
optional refinements.

- `CozyTranslate` (orchestration) → depends on a registered translator

  "Living Speech/Speaker/Translation/Voice/..." engine that wants to

## 7. Duplicate-Engine Scan

Performed the same class of check used during M387.5's `AA-004`
investigation: searched for any existing file whose real, implemented
public API already covers a proposed M388 engine's stated responsibility,
before concluding "new build required" in Section 2/3.

- **Living Speech Engine** vs. existing `cozy-speech.js`: same
  responsibility. **Would be a duplicate if built as a new, separate
  engine** rather than a thin composition wrapper (if the Living-engine
  convention requires one at all — open Plan-stage question, Section 3).
- **Living Translation Engine** vs. existing `cozy-translate.js`: same
  orchestration responsibility. **Would be a duplicate** for the
  orchestration layer specifically; the actual bundled-MT capability
  behind it is not a duplicate, since nothing bundled exists today.
- **Living Media Mixer** vs. existing `media-pipeline-manager.js`: **not**
  a duplicate — the existing file's real scope (image/filter/enhancement
  sequencing) is genuinely narrower than what a media *interpreter's*
  audio+video mixer needs (decode, replace speech track, preserve
  background audio, re-encode, sync to original video). No overlap found
  once each file's real method list was checked (same method-call-evidence
  standard `AA-004` used, not assumption).
- No other proposed engine (Speaker, Language Detector, Meaning, Voice
  [cloning], Lip Sync, Streaming, Subtitle [export]) has any existing
  same-name or same-responsibility file anywhere in the repository.

**Conclusion: the only real duplication risk is naming two new "Living"
wrappers around already-real `cozy-speech.js`/`cozy-translate.js` instead
of composing them directly — flagged for explicit Plan-stage decision, not
resolved here.**

## 8. Security / Privacy (Compose-Stage Observations Only)

- Voice cloning (Section 2, confirmed absent) inherently involves
  biometric-adjacent data (a person's real voice characteristics) —
  Rule-level guidance from this repository's own Living Security chain
  (M381–M387) has no existing policy specifically addressing voice-model
  training/storage; this needs explicit design at Plan stage, not
  assumption.
- Media file processing (decode/re-encode) at a "downloaded video/audio"
  scope implies handling third-party copyrighted content — no existing
  CozyOS policy on this was found during this Compose; flagged as an open
  question, not a blocker to Compose itself.
- `SpeechTranslationProviders`'s own "NEVER FABRICATE" convention (Section
  1) is a real, existing pattern worth carrying forward for any new
  provider this milestone adds (voice-clone providers, cloud MT providers,
  etc.) — honestly report `isReal:false` rather than fabricate output.

### Gap found: proposed implementation order omits a required first step

The proposed order (Meaning → Language Detection → Translation → Subtitle
Timeline → Voice Generation → Synchronization → Streaming/Playback →
Coordinator) assumes speech audio and background audio are already
separated from an input video file. **Nothing in the proposed order
performs that separation.** Section 5's own Dependencies list already
names the real blocker: `media-pipeline-manager.js` depends on
`codec-decoding-engine.js` (`MD-009`) for anything beyond image/filter/
enhancement — i.e., there is no existing way to even get audio *out of* a
downloaded video file today. Every downstream step (Language Detection
through Voice Generation) has no real input without this. Additionally,
`MD-010` (background/ambient audio separation — required to preserve
"background sounds and music," an explicit goal in the milestone's own
Purpose statement) and `MD-011` (speaker diarization — needed for
multi-speaker video, and to know *whose* voice to preserve/replace) are
both real dependencies of "Voice Generation"/"Synchronization" that the
proposed order also never places.

**This is a real completeness gap, not a style preference** — approving
the order as originally proposed would let implementation start on
Translation Pipeline/Subtitle Timeline with no way to have ever reached
that stage from a real video file. Per Option B, this Compose Report is
revised (not rejected outright — the architecture direction and ownership
findings remain sound) to insert the missing step and correctly place the
two other real dependencies.

### Approved Implementation Order (revised, supersedes the original 8-step proposal)

1. **Media Decode Engine** (new — resolves `MD-009`'s decode half; extracts
   audio + video tracks from a downloaded file/stream). *Prerequisite for
   every step below — nothing else can run against real media without it.*
2. **Language Detection Engine** (new — resolves `MD-012`).
3. **Translation Pipeline** (composes existing `cozy-translate.js` +
   `speech-translation-adapter.js`/`-provider.js`; absorbs what would have
   been "Living Meaning Engine," per `AA-005`'s closure above — no separate
   engine).
4. **Speaker Diarization** (new — resolves `MD-011`; needed before Voice
   Generation/Synchronization can know *which* voice to preserve per
   segment, and before background-audio separation can isolate speech from
   non-speech).
5. **Background Audio Separation** (new — resolves `MD-010`; depends on
   step 1's decoded audio and, ideally, step 4's diarization to isolate
   speech from music/ambient sound before replacement).
6. **Subtitle Timeline Engine** (new — resolves `MD-014`'s generation half;
   can start once steps 2–3 produce timed, translated segments).
7. **Voice Generation Engine** (composes existing `cozy-tts-browser-adapter.js`/
   `voice-manager.js` — generic TTS only; voice-cloning/preservation of the
   *original* speaker's voice is explicitly `MD-008`, Out of Scope this
   milestone per the original task, and is **not** promised by this
   contract).
8. **Synchronization Engine** (new — keeps generated speech timing aligned
   with the original video's speech segments; lip-sync itself remains
   `MD-015`, Out of Scope).
9. **Media Encode Engine** (new — resolves `MD-009`'s encode half; muxes
   the new audio track with the original, unmodified video).
10. **Streaming/Playback Pipeline** (new — resolves `MD-013`; live-stream
    case only, composes `cozy-live.js`'s existing room/channel/stream
    scaffolding for the multi-language-channel structure).
11. **Video Interpreter Coordinator** (new — orchestrates 1–10; the one
    engine that registers through `EngineBridge`/`PluginManager`, per this
    codebase's established pattern, and is the only new *Living Engine*
    proper in the M381–M387 startup-order sense — 1–10 above are its
    internal pipeline stages, not independent Living Engines needing their
    own startup-order slot, unless Phase 2 review for a *specific* stage
    later finds otherwise).

**Explicit, honest scope boundary for this approved contract:** this order
delivers real language interpretation with generic (not voice-cloned) TTS,
dependent on whatever real MT provider is actually registered (today: only
an optional experimental Chrome API — `MD-007` remains unresolved and out
of licensing scope), no lip-sync, and no guarantee of the ~0.5s target
until step-by-step performance is actually measured (no existing baseline,
per Section 9). Nothing above promises more than the repository can
currently deliver.
