# CozyOS Universal Voice — Application Integration Audit

**Status:** Application census complete. No per-application implementation has been made yet — this document is the required first deliverable before any such change, per the governing directive's "Important implementation rule."

**Method:** Every real `window.CozyOS.ServiceRegistry.registerApplication(...)` call site in the repository was located and traced (not inferred from filenames or documentation). `registerCoordinator(...)` calls (internal platform services/engines — Identity, Reasoning, Automation, Policy, DeveloperHub, etc.) were excluded: they are not end-user applications. This matches the repository's own convention, confirmed via `core/platform/application-visibility.js` and `cozy-knowledge-registry.js`.

## 0. The real voice exit point (confirmed by tracing code, not inference)

```
cozy-living-assistant.js #send()
  -> LivingAI.think() (active provider: rule-based-conversational-provider.js)
     -> CognitiveCoordinator.run() (Memory/Policy/Interpretation/Thinking/Reasoning)
     -> composeReply(intent, lang) / template()
  -> in parallel, CozyAnswerEngine.answer() -> CozyAdvisor.advise() tried first;
     falls back to the rule-based provider's reply when non-VERIFIED
  -> whichever text wins becomes replyText
  -> #speak(replyText)                              [cozy-living-assistant.js:1033-1055]
  -> window.CozyOS.VoiceManager.speakProgressive() / .speak()
```

This is the **one** real path any application's user-facing text can reach voice through today. No redaction/sanitization logic exists anywhere on this path (`voice-manager.js`, `living-tts.js` both grepped for redact/sanitize/secret/otp/token — no matches). See §3 for why this matters.

## 2. Live Session vs Live/Connectivity vs Media Intelligence vs Live Camera Capture — confirmed genuinely separate

All four are real, distinct `registerApplication()` calls with distinct `APP_ID`s, source files, and composed-engine sets — not the same mechanism described differently, and not sub-features of one pipeline. `cozy-knowledge-registry.js:427` itself discloses this explicitly: *"No single 'LiveOS' application exists — this entry honestly discloses that rather than fabricating one."*

Separately confirmed: `core/engines/media/` contains a large secondary media pipeline (~20 files: `media-pipeline-manager.js`, `video-interpreter-coordinator.js`, `synchronization-engine.js`, translation/streaming/subtitle/enhancement/filter/image/decode/encode/diarization engines). Only **one** file from that directory (`live-capture-engine.js`) is loaded on any real page. The rest has zero `<script src>` references anywhere — real code, but not reachable today, architecturally separate from both "Media Intelligence" and "Live Camera Capture" above (which are themselves real and loaded).

## 3. Authenticator / OTP security finding (structural gap, not a live incident)

No path exists today from a real OTP code, recovery code, or secret to `speak()` — confirmed by direct tracing (see row 8 above and the agent's full citations). However: **the shared voice chain that already speaks other conversational text has zero content-based filtering.** If any future intent handler or knowledge-registry fact-getter were ever wired to read a live OTP code or recovery code, that text would flow straight to voice with no guardrail. **This is a required fix before Universal Voice can honestly claim "never reads OTP/secrets aloud"** — see the Application Integration Matrix for the specific remediation (an explicit content filter/redaction layer at the `VoiceManager.speak()`/`#speak()` boundary).

## 4. Other findings requiring disclosure

1. **HospitalOS and SchoolOS are not real applications.** They appear only as honestly-disclosed mock/placeholder entries in `cozy-knowledge-registry.js` (lines 1085-1140) backed by legacy `core/plugins/hospitalOS.js`/`core/ai/schoolHandler.js`, which return canned text and are explicitly self-labeled as mock. Excluded from the census above; not in scope for voice integration.
2. **A family of dead/orphaned "Handler" files exists at `core/ai/`** (`agritechHandler.js`, `businessHandler.js`, `churchHandler.js`, `hospitalHandler.js`, `hotelHandler.js`, `mpesaHandler.js`, `saccoHandler.js`, `schoolHandler.js`), exporting functions literally named e.g. `processChurchVoiceIntent()` despite never being wired to any real voice output. Zero real callers outside their own files; `schoolHandler.js` even imports a module (`../../modules/wellbeing.js`) that does not exist in the repo. Flagged as a latent risk (misleading naming) should anyone wire these up without realizing they're mock — no action required unless that happens.
3. **MpesaOS's second, orphaned registration path** (`core/plugins/mpesaOS.js`) is loaded on real pages alongside the real `mpesaOS-engine.js`, but its query-handler has no live caller and is explicitly self-disclaimed as non-conversational by `core/pluginManager.js:194`. Not a live risk today; flagged as the exact pattern to watch for if it is ever wired to the Living Assistant (would become a genuine "separate voice/response path," Classification C).
4. **Testing gap**: no direct unit test files exist for `churchOS-core.js`, `shopOS-core.js`, `wholesaleOS-core.js`, `quarry-index.js`, or `authenticator.js` themselves (their submodules are well-tested; these top-level registration/entry files are not).

## 5. Deep trace: Live Camera Capture, Live Session, Live/Connectivity, Media Intelligence

Per the governing directive's explicit follow-up ("do not invent replacement status text if an existing source already exists; if no event mechanism exists, document that as a real architectural gap before implementing one"), each of the four B-classified surfaces was traced to its real UI consumer, its real status-text source, and whether any real event/callback mechanism exists underneath it — not assumed from the earlier pass's file-level classification.

### 5.1 Live Camera Capture

- **Real UI consumer**: `core/engines/video/ui/cozy-live-camera-capture-dashboard.html` (a standalone page — never loaded inside `dashboard.html`/`index.html`). Every status string ("Preview started.", "Recording started (...).", "Capture failed: ...") is constructed **inline, once, synchronously**, directly from the `await appApi.startPreview()`/`.capturePhoto()`/etc. return value inside each button's own click handler (`resultDiv.textContent = ...`). There is no reactive re-render.
- **A real event mechanism exists one layer down, currently with zero subscribers.** `core/engines/video/live-video-capture-engine.js` (`window.CozyOS.LiveVideoCapture`) has its own private `#listeners`/`#emit()`/`on(eventName, handler)` and genuinely fires `cameraConnected`, `previewStarted`, `error`, `previewStopped`, `cameraDisconnected`, `photoCaptured`, `recordStarted`, `recordStopped`, `recordPaused`, `recordResumed`. A repo-wide grep for `LiveVideoCapture....on(` found **no callers anywhere** — this is a live, disclosed, but entirely unused broadcast. The App facade (`cozy-live-camera-capture-app.js`) that registers the application never subscribes to it either; it only calls the engine's request/response methods and returns their results directly (confirmed pure passthrough, no event/callback surface of its own).
- **Not available to the shared Live Window today — and for a more fundamental reason than "no bus exists."** `live-video-capture-engine.js` itself is **not `<script>`-loaded** on `dashboard.html` or `index.html` (grep confirmed no match on either file); only the App facade is loaded there. On the actual pages that host the shared Live Window, `window.CozyOS.LiveVideoCapture` does not exist today, so the App facade's methods would hit "engine not loaded" branches rather than reporting real capture status.
- **What VoiceManager could safely consume, and what's missing to get there**: the engine's real events carry real, honest payload fields (`deviceId`, `mimeType`, `sizeBytes`, `durationMs`, `message` for errors) — a bridge could construct honest sentences from them ("Recording started.", "Camera error: " + event.message) the same way ChurchOS's `record-church-member` intent already turns a real result into "Member added." This is not inventing replacement text (no competing human sentence exists yet for these events — the dashboard's inline strings are a separate, page-local construction, not a canonical source being duplicated). But two real, additive gaps must close first: (1) `live-video-capture-engine.js` must be script-loaded on the shared pages, (2) a bridge must call its real `on(...)` and route through the voice chain — see §5.5 below for why even that last step needs one more small addition first.

### 5.2 Live / Connectivity

- **Real UI consumer**: `core/connectivity/ui/cozy-live-connectivity-dashboard.html` (standalone). `getConnectivityOverview()`, `getQueueStatus()`, `getLocalDevices()`, `getConnectivitySessionState()` are each called **once, synchronously, at page render time** and written directly to DOM text. No polling, no re-render on change, confirmed by reading the full render function.
- **No event mechanism exists anywhere in this surface's real code** — a targeted grep for listeners/`#emit`/`on(eventName`/`addEventListener`/`dispatchEvent` in both `cozy-live-connectivity-app.js` and `core/connectivity/cozy-living-connectivity.js` found zero matches. This is a genuine, disclosed absence, not an oversight in this trace — unlike Live Camera Capture, there is no lower-layer emitter to bridge to.
- **Not available to the shared Live Window today**, and for the same page-loading reason as §5.1: `cozy-live-connectivity-app.js` is loaded on `dashboard.html`/`index.html`, but `core/connectivity/cozy-living-connectivity.js` (the real capability-detection engine underneath it) is not.
- **Real architectural gap, not fabricated**: making this surface's status voice-reachable would require building new reactive plumbing inside `cozy-living-connectivity.js`/`cozy-connectivity-transport.js` themselves (real engine-level work), not just wiring an existing broadcast — a materially larger change than the other three rows. Documented here rather than worked around.

### 5.3 Live Session

- **A real, rich event mechanism already exists.** `core/modules/communication/ldce-session-engine.js` (`window.CozyOS.LDCESessionEngine`, a true singleton) has its own private `#listeners`/`#emit()` firing real lifecycle events: `session-created/started/paused/resumed/ended/cancelled`, `participant-joined/left/invited/role-changed/language-changed/state-changed`, `metadata-changed`, `translation-session-linked`, `signaling-offer-sent/answer-sent/complete`. It also writes real, human-readable strings via its own `#logToTranscript()` ("Session started.", "Session paused.", "Session resumed.") today — these are genuine, existing text, not something this trace is proposing to invent.
- **A second real event source composes the first.** `LDCEMediaSessionEngine` fires `connection-state-changed` (a real passthrough of actual `RTCPeerConnection` state — confirmed by its own comment, not a fabricated status). `core/shell/live/ldce-live-media-coordinator.js#startHostMedia()` already subscribes to it (`media.on('connection-state-changed', ...)`) and to `LDCESessionEngine.on('participant-joined', ...)`, translating both into `onViewerConnectionResult`/`onSecondViewerRejected` callbacks. `core/shell/live/ui/cozy-live-host-console.html` (a separate, standalone "Go Live" page — deliberately not part of `dashboard.html`, per its own header comment) already renders these as real strings today: "Viewer connected.", "Viewer disconnected. Waiting for a viewer…", "Live with one viewer. Additional viewers are not supported in this stage."
- **Available to the shared Live Window structurally, today, with zero new script loads.** `dashboard.html` already loads `ldce-session-engine.js` (line 708) on the exact same page as `cozy-living-assistant.js` (line 745). Because `LDCESessionEngine` is a page-wide singleton, any code running on that page can call `.on(...)` on it right now — this is the one surface among the four where the real event source is already present on the shared Live Window's own host page.
- **ChurchOS precedent checked, gap confirmed universal.** `core/modules/ChurchOS/church-live-session-controller.js` already composes `LDCESessionEngine.createSession()` for real worship sessions (an already-completed integration from earlier work in this repo), but it never calls `.on(...)` on the engine and has no `VoiceManager`/`speak` reference anywhere in the file. So the gap is not specific to the standalone host/join consoles — even ChurchOS's own live-worship flow does not forward session events to voice today.
- **One more real gap found, upstream of all of this**: `cozy-living-assistant.js` has **no existing public method that accepts arbitrary text and calls its private `#speak()`.** The one method that looks like a candidate, `announceContext(hintText)` (line 475, built for InterestOS's cross-page "Ask CozyAI" hand-off), calls only `this.open()` + `this.#addMessage(...)` — confirmed by reading it — it is **visual-only** and never reaches voice. There is currently no public "speak this real status text" entry point on the one voice authority for a caller that isn't itself a user question. This is the real, additive extension point Matrix Phase 2 onward needs — not a new VoiceManager, not a second `#speak()`, but a small, honest extension of this one already-existing method (or an equally narrow sibling of it).

### 5.4 Media Intelligence

- **Real UI consumer**: `core/modules/intelligence/media/ui/cozy-media-intelligence-dashboard.html` (standalone). `answerMediaQuestion(question)` is called directly from one button's click handler; its real, disclosed answer text is written straight to `answerEl.textContent`. Grepping `cozy-media-intelligence.js` for listeners/`#emit`/`on(`/`addEventListener`/`dispatchEvent` found nothing — confirmed no event mechanism, matching the earlier pass's finding.
- **This is not a reactive-status problem at all.** `answerMediaQuestion()` is already a real, synchronous, non-fabricated Q&A function — there is no "status change" to announce, just an answer to compose into the existing chain. `CozyMediaIntelligence` (the facade) **is** already `<script>`-loaded on both `dashboard.html` and `index.html` today, unlike the engines in §5.1/§5.2 — fully reachable from the shared Live Window's page context right now, zero new script loads required.
- **The real gap is compositional**: nothing in `cozy-answer-engine.js`/the rule-based provider/`cozy-ai.js` calls `answerMediaQuestion()` as an evidence source the way `CozyKnowledge` is already composed (confirmed by the original audit's repo-wide grep: zero callers outside its own dashboard). This is genuinely different in kind from §5.1-5.3 — an evidence-source wiring task, not an event-bridge task — matching the Matrix's own classification.

### 5.5 What this means for implementation order

Of the four, **Live Session (§5.3) has the smallest real gap** — the event source and the human-readable text already exist and are already loaded on the shared page; only the voice-authority-side entry point (`announceContext`-style extension) and a small subscription bridge are missing. **Live Camera Capture (§5.1)** needs the same voice-authority extension plus a real, disclosed engine-loading gap closed first. **Live/Connectivity (§5.2)** needs new reactive plumbing inside the connectivity engine itself before there is anything to bridge — the largest of the four. **Media Intelligence (§5.4)** needs answer-chain composition, not event bridging, and is already fully reachable.

## 6. What this audit does NOT yet cover

Per-application implementation (wiring B-classified apps' status/notification text into the shared voice chain, and building the OTP content-filter guardrail) has **not** been started beyond the Authenticator guardrail already completed. That work is scoped in `VOICE-APPLICATION-INTEGRATION-MATRIX.md`, now updated with the real evidence from §5 above.
