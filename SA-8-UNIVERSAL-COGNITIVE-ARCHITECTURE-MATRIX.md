## SA-8 Phase 1 — Clarification Intelligence (implemented, tested, regressed this pass)

**The verified gap**: `window.CozyOS.SemanticIntentEngine.analyze()` (`core/living/cozy-ai-semantic-intent.js`) already has a real, working `buildClarificationQuestion()` — constructing a genuine, bilingual clarifying question for the `"competing_goals"` ambiguity case (e.g. "Do you want to buy X, or would you like to understand how it helps you first?"). `rule-based-conversational-provider.js` already surfaces this real question to users for its own reply path. **`cozy-answer-engine.js` never consulted it at all** — its own final, context-less fallback (`ctxResults.length === 0`) always returned a generic "I don't have verified information to answer that yet" message, exactly the "Bado sina jibu" pattern the directive explicitly forbids, even when a real, honest clarifying question was available from an already-loaded, already-tested authority.

**What was implemented** (`core/modules/intelligence/answer/cozy-answer-engine.js`): before the generic fallback, call `SemanticIntentEngine.analyze(question, { previousEntity: entityHint, ... })` (the exact same real call shape `rule-based-conversational-provider.js` already uses) and, when it returns a real `clarification.question`, return that instead of the generic text. No new engine, no new template store, no second clarification mechanism — this composes the one real existing authority into a path that previously never saw it.

**Deliberately not done in this sub-phase**: `SemanticIntentEngine` currently only builds a real clarifying question for the `"competing_goals"` ambiguity reason. The other two reasons (`"no_pattern_matched"`, `"short_low_evidence_no_entity"`) still fall through to the generic text, because — traced directly — `"short_low_evidence_no_entity"` is defined to fire only when NO entity was found at all (`!entity.value` is part of its own trigger condition), so there is nothing concrete yet to build a useful clarifying question about for that case. Extending clarification-question construction to those other ambiguity reasons is real, additional work for a future SA-8 sub-phase, not attempted here to keep this phase small and fully verified.

**Tests**: 6 new DI-based unit tests (`cozy-answer-engine-clarification-intelligence.test.js`, using the real, unmodified `cozy-ai-semantic-intent.js` — not a fake) + 3 new real-browser Live Window E2E tests (`cozy-answer-engine-clarification-intelligence-browser.test.js`), confirming: a real ambiguous question receives the real clarifying question and not the generic fallback; the returned text matches the engine's own real output exactly; an ordinary question is unaffected; the engine-absent and engine-throwing cases degrade honestly; a real-evidence case short-circuits before this step; and the same resolved clarifying-question text reaches `VoiceManager` through the existing, unmodified `#speak()` chain. All passing.

## Why the largest gap (§4/5, fresh generative construction) was not attempted this pass

The directive explicitly warns: "Do not reduce SA-8 to 'use an LLM to generate a sentence.'" Building a genuine, safe, deterministic (or locally-model-backed) sentence GENERATOR — composing morphology (`cozy-kiswahili-structural-analysis.js`), the semantic plan's claims, and evidence into a grammatically correct novel sentence, with real validation (extending SA-5) — is real, substantial, multi-file work requiring its own dedicated design and test pass, not a same-turn addition alongside Clarification Intelligence. Attempting it hastily here would risk exactly the "fabricate success" outcome the directive forbids. It remains the single most important next SA-8 sub-phase, and this matrix names it precisely so a future pass does not need to re-discover it.

## SA-8 Phase 2 — Fresh Generative Sentence Construction (this pass)

**Real, empirical audit before any code change**: probed the live `dashboard.html` with the directive's own four novel human-benefit-shaped questions (2 Kiswahili, 1 English, 1 code-switched). All four produced the IDENTICAL generic ChurchOS description via `cozy-answer-engine.js`'s OLD `classifyContextIntent()`/`synthesizeFromContext()` path (`intent: APPLICATION_INFORMATION`), never engaging SA-3/SA-4 at all. Calling `SemanticAnswerPlanner.planAnswer()` directly on the same questions showed why: `SemanticIntentEngine.analyze()` found `primaryIntent: UNKNOWN_INTENT`, `goal: null`, `ambiguity.reasons: ["no_pattern_matched"]` — the real primary engine's own `GOAL_MAP` and this file's own pre-existing `SUPPLEMENTARY_GOAL_PATTERNS` (`umuhimu`/`faidika`/`important`/`benefit`, `changia`/`mchango`) cover only literal "importance/benefit" NOUNS, not the ordinary verbs "help"/"saidia" or "kupunguza" (reduce) the four real questions actually used. **This was the real, traced root cause — not a missing generator, but a goal-classification gap upstream of SA-4's already-real COMPOSED construction.**

**What was implemented** (all in `core/modules/intelligence/semantic-answer/planning/semantic-answer-planner.js` — the one, existing, already-disclosed SUPPLEMENTARY_GOAL_PATTERNS/resolveGoal() extension point from SA-3; no new file, no new engine):

1. Added `/saidia/i` (sw) and `/\bhelp(?:s|ed|ing)?\b/i` (en) to `HUMAN_BENEFIT`; added `/punguza/i` (sw) and `/\breduc(?:e|es|ing)\b.*\bwork\b/i` (en) to `PRACTICAL_WORK_CONTRIBUTION`. Closes the exact, empirically-confirmed gap above.
2. **Regression discovered and fixed in the same pass**: running the existing suite immediately after step 1 broke `"I want to buy ChurchOS but how does it help me?"` (a real `competing_goals` ambiguity fixture) — the new broad "help" pattern let the supplementary layer silently resolve it to `HUMAN_BENEFIT` instead of reaching SA-8 Phase 1's real clarifying question. Fix: `resolveGoal()` now skips the supplementary layer entirely whenever the real engine's own `ambiguity.reasons` includes `"competing_goals"` — that reason means two genuinely different real intents were detected, which is structural ambiguity about WHICH goal the user wants, never something a narrow regex is entitled to silently pick a side on. Every other ambiguity reason (e.g. `"no_pattern_matched"`, meaning nothing is competing, the engine simply has no rule) still reaches the supplementary layer exactly as before. Verified by the new regression-guard tests below; the original Phase 1 clarification-intelligence suite still passes unchanged.
3. **`rankClaimsByRelevance()`** — the actual "fresh, per-question construction" mechanism, added at the one point SA-3 builds `claims` from `authoritative` evidence. Real trace: two different novel phrasings of the same resolved goal ("...attendance ya branches zetu?" vs "...waumini wengi na matawi kadhaa?") produced byte-identical composed answers even though real, grounded attendance-specific evidence already exists (`humanBenefitsSw`: "mwonekano bora wa mahudhurio na taarifa muhimu za kanisa") — it was simply never surfaced first, because claims were always emitted in fixed evidence-authoring order regardless of what the specific question asked. The fix ranks the SAME claims (never adds, drops, or invents one) by real keyword overlap between the question's own normalized text and each claim's own already-verified text, promoting the most relevant evidence to the front. When nothing overlaps, the original order is left completely unchanged — verified explicitly by a dedicated "HONEST FALLBACK" test, so this never fabricates a false distinction between two questions when the evidence base genuinely has nothing more specific to say (confirmed for the real "matawi"/branches case: no evidence field in `cozy-knowledge-registry.js`'s `churchos` entry mentions branches specifically, so both phrasings correctly and honestly receive the same general grounded answer — this is Response-Hierarchy tier B being properly preferred over inventing tier-C content, not a flaw).
4. **Minimal, real latency instrumentation** (`cozy-answer-engine.js`'s `tryConstructSemanticAnswer()`): records `semanticInterpretationAndEvidenceMs` (0 when `cognitiveResult` was already computed earlier this turn and honestly reused, never re-timed), `generationMs` (SA-4 realization + SA-5/6 validation/repair), and `totalMs`; surfaced additively as `constructionTiming` on `answer()`'s return value. Scope, disclosed honestly: this covers the SA-3/SA-4 construction stage only, not first-text/first-speech-availability at the Live Window/VoiceManager layer — extending instrumentation to that layer is real, undone work, named here rather than silently skipped.

**Gemini generative-provider boundary (§9/10) — explicitly resolved as: do not touch, document only.** Traced the real, existing infrastructure: `core/living/providers/gemini-cloud-provider.js` (`createGeminiCloudProvider()` — real, same-origin `/ai/gemini` backend call, honest `{success:false, reason}` failure discipline, never holds an API key) is registered as `"gemini-api"` into `LivingAI`'s provider registry by `gemini-cloud-provider-bootstrap.js`, but `setActiveProvider()` is deliberately never called — `"reasoning-pipeline"` remains active. `CozyLivingAI.think()` has no per-call provider override (always the single global active provider), so nothing in this phase's real path (`SemanticAnswerPlanner`/`LanguageRealizer`, neither of which calls `LivingAI` at all) can accidentally reach it. **Decision**: this phase does not activate it and does not build a per-call override — doing so was not required to close the actual, empirically-confirmed gap (a goal-classification/claim-selection problem, not a missing text generator), and activating a cloud provider un-requested would violate the directive's own "do not auto-activate Gemini merely because it exists" instruction. The system remains fully capable offline: every construction verified this phase (Kiswahili, English, code-switched, context-switched) ran with zero network calls, using only `SemanticIntentEngine` + `VerifiedEvidenceAdapter` + SA-3/SA-4/SA-5/SA-6. **Remaining gap, honestly named**: no online-enhancement tier exists yet for when SA-3/SA-4's grounded evidence genuinely lacks the specificity a question needs (e.g. a real "matawi"/multi-branch-specific evidence gap, confirmed above) — building that safely (respecting the feature-gate/credential/rate-limit/timeout/one-provider-architecture constraints §9 lists) is real, substantial, separate work, not attempted here.

**Tests added**: `semantic-answer-planner-sa8-phase2.test.js` (11 unit tests: the 3 new pattern additions in sw/en/code-switched form, the competing-goals regression guard proven both end-to-end and at the `resolveGoal()` unit level, a non-regression control proving `"no_pattern_matched"` still reaches the supplementary layer, three relevance-ranking tests — real promotion, honest no-op fallback, and a never-drops/-invents-a-claim invariant — and the critical "ACTION goal never routed to SA-3/SA-4" test) + `cozy-answer-engine-fresh-construction-browser.test.js` (8 real Live Window E2E tests: novel Kiswahili/English/code-switched human-benefit questions all receiving the real SA-4 COMPOSED sentence — not clarification, not the generic fallback; subject continuity across a follow-up; context switching + a bare pronoun-less follow-up resolving to the newly-named entity's own construction; a non-fabrication adversarial test confirming the real "does not implement" face/voice-recognition disclosure is preserved; the critical "remind me tomorrow" ACTION request never receiving a fabricated HUMAN_BENEFIT-shaped answer; and voice synchronization — the exact same resolved text reaching `VoiceManager`). All 19 new tests passing; full existing `semantic-answer-planner.test.js` (42), `cozy-answer-engine` suite (29), and `semantic-answer`/`cognitive-providers`/`phase6-semantic-intent-engine` suites (77) re-run and passing with the Phase 2 changes applied — see the final commit-gate report for the consolidated count.

**Explicitly not attempted this phase** (real, disclosed, next-gap material, not silently skipped): a true `MODEL_GENERATED` sentence generator (SA-4's own header still correctly names this as not built); a per-question online-enhancement tier via the dormant `gemini-api` provider; first-text/first-speech-specific latency instrumentation at the Live Window/VoiceManager layer; extending relevance ranking to a genuine semantic/embedding match (today it is real lexical keyword overlap only — honest about its own limits, e.g. it cannot bridge "attendance" (en loanword) to "mahudhurio" (sw) without a literal shared token); the full COMPARISON/PROBLEM_SOLUTION/TRANSLATION response-mode coverage the directive lists (HUMAN_BENEFIT/PRACTICAL_WORK_CONTRIBUTION were the two goals the real, traced gap actually involved).

## SA-8 Phase 3 — Human-Benefit Answering + Permanent Security Boundary (this pass)

**Scope decision, explicit and deliberate**: the governing directive for this phase (20 sections) asked for fresh construction, human-benefit framing, a permanent security boundary, conversation intelligence, multi-provider compatibility, an imagination/hypothetical-vs-fact distinction, and an extensive novel-input matrix, but also explicitly warned: "keep Phase 3 focused... those should remain separate verified phases unless the actual code trace proves they are inseparable." Multi-provider scoring (§13) and the imagination/hypothetical-vs-fact system (§14) were traced only far enough to confirm nothing in this phase's own change requires them, then deliberately deferred — see "Explicitly not attempted" below. The one genuinely new capability built this phase is the permanent security boundary (§6/7), because the audit below found it closes a real, currently-exploitable gap.

**Real, empirical audit before any code change**: probing the real dashboard.html's ChurchOS answer (`"Niambie kuhusu ChurchOS."`) found that `APPLICATION_HUMAN_PURPOSE_DATA.churchos`'s own `implementedAwaitingConnection`/`partiallyImplemented` fields (`cozy-knowledge-registry.js` — authored for internal audit disclosure, quoted verbatim in this repository's own `*.md` audit reports) contain real source file paths and function-call syntax, e.g. *"core/modules/intelligence/media/cozy-media-intelligence.js's real, working searchByPersonReference()"* — and this exact text reaches the real Live Window's visible answer via the existing `getContext()`/`synthesizeFromContext()` path. Checked first whether this was already covered: `core/living/tests/live-window-privacy-adversarial.test.js` (Wave 6) is a real, existing adversarial security suite, but its own `LEAK_PATTERNS` target ACCIDENTAL leakage (stack-trace shapes, `process.env`, `require(`, thrown-error text) for prompts trying to provoke a crash — none of those patterns match this well-formed, intentionally-authored sentence, so Wave 6's suite passes today even though the leak is real. This is a genuine, previously-unclosed gap, not a duplicate of existing coverage.

**What was implemented**:

1. **`core/modules/intelligence/answer/cozy-answer-security-boundary.js`** (new file) — `window.CozyOS.AnswerSecurityBoundary.sanitize(text)`/`.detectLeaks(text)`. Three narrow, real patterns: a relative-or-bare filename ending in a real code/document extension (`.js`/`.html`/`.css`/etc.); a bare identifier immediately followed by literal empty `()` (real function-call syntax — verified against this repository's own evidence data to produce zero false positives on ordinary parenthetical prose, which always either has a space before `(` or real content inside it); and internal architecture class-name vocabulary (`Engine`/`Registry`/`Adapter`/`Provider`/`Coordinator`/`Contract`/`Realizer`/`Planner`-suffixed identifiers), explicitly guarding the 8 real CozyOS product names so they are never mistaken for internal vocabulary. A punctuation-cleanup pass removes the most common redaction artifacts (double spaces, orphaned em-dashes). This is presentation-layer redaction only — never an authorization boundary; SA-2's own sensitivity/PUBLIC evidence filtering and every application's own permission checks remain entirely upstream and untouched.
2. **`core/modules/intelligence/answer/cozy-answer-engine.js`** — the pre-existing `answer()` function (11 internal return points) was renamed to `answerInternal()` unchanged, and a new, thin `answer()` wrapper added that calls it once and sanitizes only the final `answer` string through `AnswerSecurityBoundary` before returning — one universal choke point covering every branch (FAQ router, SA-3/4 construction, the old context-synthesis path, clarification, error fallbacks) rather than 11 individual edits where a future new branch could silently skip it. Degrades honestly to the original, unsanitized behavior when `AnswerSecurityBoundary` is not loaded (every pre-existing test's minimal fake `window.CozyOS` — confirmed zero regression).
3. **Script wiring**: `cozy-answer-security-boundary.js` added before `cozy-answer-engine.js` on every real page that loads the engine — `dashboard.html`, `index.html`, `admin-workspace.html`, `applications/InterestOS/interestos.html` — so the boundary is genuinely the permanent, page-wide rule the directive asked for, not a single-page demo.

**Empirically verified end-to-end** (not just unit-level): the exact, previously-leaking real ChurchOS answer was re-probed after the fix — `AnswerSecurityBoundary.detectLeaks()` on the live Live Window's final reply now returns `[]`. Real product names (`ChurchOS`/`QuarryOS`/`ShopOS`/`InterestOS`/`CozyOS`) confirmed to survive sanitization unaffected in the same real reply.
